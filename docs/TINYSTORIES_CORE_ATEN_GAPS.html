Decomposition removes the raw graph's TorchAO calibration/quantization calls, tensor-subclass accessors, in-place additions and in-place detaches. Their source counts before/after decomposition are in the JSON report. Embedding remains present and is recognized; the export path does not have the live-weight compiler refusal.

Whole-model import: unsupported. aten.index.Tensor of a bool tensor is not imported. The native INT32 matrix-product refusal appears after isolating the frontend indexing blocker. Local rule recognition alone does not establish native IR acceptance or numerical equivalence.

Is this exactly the “~180 operators”?

The graph has 34 distinct Core-tagged operators. All numerical ATen calls are Core-tagged. The non-Core scaffolding consists of metadata assertions and tuple projections. The raw graph's 49 aten._int_mm.default calls become 49 Core aten.mm.default calls. Each product explicitly widens both INT8 operands to INT32 first; merely renaming the INT8 operation would change its result dtype.

A small control uses the same decomposition and agrees with _int_mm in PyTorch. TorchLean refuses the INT32 matrix-product IR record. Supporting an operator name alone does not establish support for every dtype or accumulator contract.

Quantized behavior preserved in PyTorch

All 49 linear layers use INT8 weights and dynamic per-token INT8 activations. The decomposed graph expresses those 49 products as INT8→INT32 casts followed by INT32 matrix multiplication. This reference representation does not prescribe 32-bit storage or multipliers for an eventual FPGA implementation.
